# Overmind OVM Operator Chat — Requirements (locked 2026-05-21)

Add an interactive "OVM" operator console to the AGJAssist workflow dashboard: a chat with a persistent Sonnet ("overmind brain") that knows the whole app + can inspect/adjust workflows. AGJAssist, branch feat/overmind. Reuse existing infra (tmux lifecycle, WS pane streaming + input, ConversationService, terminal-chat-state.js).

**OU1 — Operator-control HTTP endpoints (localhost + OVERMIND_TOKEN).** So the OVM brain can ADJUST workflows via curl (it has bash). Add token-guarded localhost endpoints mirroring the Telegram controls: POST /api/overmind/workflows/:id/pause, /resume, DELETE (drop) — and confirm tasks/rename/register already exist. (rename = JWT W3; these new control ones use the same OVERMIND_TOKEN localhost guard as register/tasks.) Read = existing GET /api/overmind/workflows.
*Acceptance:* curl with token can pause/resume/drop a workflow; bad/no token → 401; reflected in the dashboard.

**OU2 — OVM session manager (open-reuse / restart / close) + operator primer.**
- Operator primer doc (in repo, e.g. plan/overmind/OVM_OPERATOR_PRIMER.md): full AGJAssist+overmind feature set, the known quirks/lessons, schema, workflow lifecycle, and the EXACT inspect (GET workflows) + adjust (the OU1 endpoints + rename/tasks) commands incl the token, and the rule: destructive/irreversible actions (drop, end, anything touching real coordinator sessions) → PROPOSE and wait for JROM's confirmation in chat; manage only via overmind's own controls (do NOT send keystrokes into real coordinator tmux sessions).
- Endpoints (JWT auth, browser-driven): POST /api/overmind/ovm/open (create tmux session "OVM" with cwd=AGJAssist dir, launch `claude --dangerously-skip-permissions --model sonnet`, then send a kickoff message: "Read <primer path> and operate as the Overmind operator per it. OVERMIND_TOKEN=<token>. Confirm when ready." — REUSE if session already exists, do not relaunch), POST /api/overmind/ovm/restart (terminate + open fresh), POST /api/overmind/ovm/close (terminate), GET /api/overmind/ovm/status (open? since when?).
- Use tmuxService.sessionExists("OVM") for reuse detection; createSession/terminateSession; the 3-call send for the launch + kickoff.
*Acceptance:* open creates+launches+primes OVM (or reconnects if already open); restart relaunches fresh; close kills it; status reflects reality.

**OU3 — OVM tab UI.** A 4th tab "OVM" beside Active/Completed/History. Renders a live chat/terminal view of the OVM session (reuse the tmux WS stream /ws/tmux/OVM... + input box → send-keys), with Open / Restart / Close buttons + a status dot. Input sends to the OVM pane; output streams live. Chat-styled (use terminal-chat-state friendly formatting).
*Acceptance:* OVM tab shows the live session; typing sends to OVM and the reply streams back; buttons open(reuse)/restart/close work.

**Constraints:** reuse existing tmux/WS/conversation infra; localhost+token for control endpoints; the claude session is --dangerously-skip-permissions (full bash) so scope is enforced by the PRIMER (instruction), not a sandbox — primer must be explicit about overmind-controls-only + confirm-destructive. Preact/HTM no-build; deploy npm run build; commit per batch; live-smoke.

## Injected 2026-05-21 (resilience)
**OU5 — Telegram startup/polling must be non-fatal.** A Telegram network blip currently CRASHES the whole app at startup ("Fatal startup error: RequestError: AggregateError" from the bot's request lib), taking the local API/dashboard/overmind down. Fix: the local server (API + dashboard + overmind watcher) MUST start and stay up regardless of Telegram reachability. Wrap the bot startup (start/polling/setMyCommands) so failures LOG and CONTINUE (with background retry), never throw fatally or exit the process. Add process-level guards (unhandledRejection/uncaughtException from the bot's network lib should be logged, not crash). The dashboard/overmind must work with Telegram fully down.
*Acceptance:* with Telegram unreachable, the process still boots, /app.js + /api/overmind/* respond, the watcher runs; the bot logs polling errors + retries in the background without crashing.

## Injected 2026-05-21 (URGENT — classifier false-"working" bug)
**OU6 — Activity must be judged by pane CHANGE, not stale marker text.** BUG (live, lkcamp): a stuck coordinator (pane FROZEN, empty composer, waiting to review codex's proposal) was classified `working` forever — because the busy-marker regex matched incidental "Waiting for" text in the idle recap/task list. So overmind never marked it stuck → never nudged → both coordinator+child sat stuck. Root flaw: in src/services/overmind-watcher.ts the classifier treats BUSY_MARKER presence as "working" even when the pane is frozen (classifyWorkflow ~line 133: `hasBusyMarker || coordinatorHashChanged || mtimeAdvanced`; parent ~line 178 and child ~line 203 also marker-only).
Fix: "working" must require ACTUAL CHANGE — coordinator pane hash changed since last tick, OR run_dir mtime advanced, OR a CHILD pane hash changed since last tick. The mere presence of a busy-marker on an UNCHANGED pane must NOT count as working. Track child pane hashes across ticks (in-memory in the watcher keyed by workflow id is fine; coordinator hash already persists in last_pane_hash). Apply to all three classifications (overall, parent_status, child status). Remove "Waiting for" from / retire the standalone busy-marker working-trigger.
*Acceptance:* a frozen coordinator pane containing "Waiting for" (or any marker) text → accrues stuck_since → becomes `stuck` after threshold → gets nudged. A genuinely changing pane → working. Coordinator frozen but a child pane changing → overall working (child is progressing, don't nudge). Both frozen → stuck → nudge.

## Injected 2026-05-21 (data-driven proper detector — replaces O6/O7 heuristic)
**OU7 — Deterministic IDLE detection: body-frozen + no-active-turn (zero per-tick tokens).** Study of 98 real session-samples (spark+sonnet ground truth): frozen-pane→idle is 100% reliable; "changed pane" is only 47% working — the other 53% are idle with CHROME drift (monitor counts, recaps, scrollback, ticking timers). Normalization (O7) caught 0. So: judge activity on the CONVERSATION BODY only, ignoring chrome. Rule (per session): WORKING ⟺ (an active-turn indicator "esc to interrupt" is present) OR (the BODY hash changed since last tick). IDLE ⟺ no active turn AND body frozen. extractBody(pane) strips: the bottom composer line(s) (❯/› + content), the persistent status/hint bar (lines containing "bypass permissions","ctrl+t","to manage","← for agents","↓ to manage","/ps to view","/stop","N shells","N monitors", model/cwd footers like "gpt-5","Sonnet …· ~/"), horizontal-rule lines, AND spinner/timer lines ("esc to interrupt", "Working (Ns)", "Waiting for … (Ns)", a spinner glyph ◦•✻✶✢●○ + verb + "(…s)"). Use the BODY hash for coordinator + child change detection (replace the O7 normalize-hash). Then idle accrual → stuck as before.
*Acceptance:* an idle pane whose only delta is chrome/timer (body frozen, no active turn) → IDLE → after threshold stuck/nudge. A pane with an active turn or growing body → working. Zero LLM calls in the tick loop.
